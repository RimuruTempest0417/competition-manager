# v2.22.0 — 候補再補強：拖拉排序、跳到第 N 位、順位異動紀錄、匯出補欄位

**發佈日期**：2026-09-26｜**類型**：P1 賽事與報名核心（Roadmap P1-2 第三輪補強）

## 為什麼要做

v2.21.0 給了「指定遞補」與「候補順位手動調整」，但實際坐在電腦（或手機）前面操作時，還有四個地方卡卡的：

1. **想把人從第 8 位搬到第 2 位，得按 6 次「↑」**——每次都要等一次 API 回來，還要重新渲染整份名單。
2. **搬動的方式太隱晦**：只有 ↑／↓ 兩個按鈕，看得出來「怎麼調」的人不多；手機上用手指拖拉是最直覺的，但那需要真的做。
3. **調完之後看不出「誰在什麼時候調了什麼」**：稽核日誌在另一個頁面，主辦在爭議發生時要找半天。
4. **匯出的報名名單看不出狀態與順位**：現場報到時只看到姓名與隊伍，不知道誰已核准、誰是候補第幾位。
5. 還有一個**這個版本才發現的老問題**：報名名單 CSV 匯出其實壞掉很久了——檔案下載成功，打開卻是一堆空行（詳見最後一節）。

## 新增

### 1. 拖拉排序（手機也能用）

候補每一列左側多了拖曳把手 **⠿**：按住往上／往下拖，放手才送出。

- 用 **pointer 事件**（不是 HTML5 drag and drop，也不用任何外部套件）：手機的觸控、桌機的滑鼠走同一條程式碼路徑。
- 把手有 `touch-action: none`，手指拖曳不會變成「捲動頁面」（沒寫這個的話手機永遠拖不動，這是最常見的坑）。
- **拖動時只動畫面**，放開才送一次 API（完整順序），由後端驗證；失敗會把畫面拉回真實狀態並說明原因。
- 只按一下把手（沒有實際拖動）不會送 API。

### 2. 「第 N 位」下拉：一次搬到任意順位

每一列的下拉列出「第 1 位…第 N 位」，選了就搬過去（取代連按 ↑／↓）。

- 也順便照顧**沒有滑鼠、只能用鍵盤**的人：下拉可以用鍵盤操作，拖拉不行。
- 選到目前的位置不會送 API（只提示「這一筆已經在那個順位了」）。
- 兩人同時在調時：後端驗證名單一致性，對不上就整批拒絕並要求重新整理（v2.21.0 的行為不變）。

### 3. 「🕘 順位異動」紀錄面板

候補區塊多一顆「🕘 順位異動」，展開後看到最近 30 筆跟候補有關的紀錄：

- 涵蓋 `REORDER_WAITLIST`（調整順位）、`PROMOTE_WAITLIST`（手動／指定遞補）、`AUTO_PROMOTE_WAITLIST`（取消自動遞補）、`REGISTER_APPROVED`／`REGISTER_REJECTED`（審核）、`WAITLIST_NOTIFY`（通知設定）、`CANCEL_REGISTRATION`（取消報名）。
- 每筆顯示：時間、中文動作名稱、操作者、內容（例如「調整候補順位（3 人）: 1.waitB、2.waitC、3.waitA」）。
- 端點 `GET /api/competitions/:id/waitlist/history?limit=30`（管理員以上，上限 100 筆）。
- **乾淨的來源**：直接讀稽核日誌（不另開一張表），所以「紀錄」與「稽核」永遠是同一份資料，不會有兩套說法。

### 4. 遞補通知開關（每個賽事自己決定）

候補區塊多一個勾選框「遞補時推播通知對方」（預設開啟）。

- 需要時可以關掉：例如主辦正在連續調整名單（先遞補 A、再取消、再遞補 B），中途通知只會讓對方一頭霧水；或實際聯絡是另外用電話／群組做。
- **關掉的是「通知」，不是「遞補」**：狀態、名單、稽核全部照常，只是**完全不碰推播**（連查訂閱都不查 —— 測試有驗）。
- 三條遞補路徑都遵守：指定遞補、遞補下一位、以及**有人取消正取時的自動遞補**。
- 關閉狀態下，介面回報會寫明「依賽事設定未通知」，稽核內容也記「未通知（依賽事設定）」——事後查得到為什麼對方沒收到通知。
- 設定變更留稽核 `WAITLIST_NOTIFY`；重複設定同一個值不會重複寫紀錄。
- migration：`migrations/2026-09-26-v2.22.0-waitlist-notify.sql`（`competitions.waitlist_notify`，可重複執行）。**未執行時一律視為「通知＝開啟」**（既有行為不變），介面把勾選框變成停用並說明要先執行 migration，端點回 `503` ＋檔名指引。

### 5. 匯出報名名單多了「狀態」與「候補順位」

現場報到用的 CSV 現在直接看得出誰已核准、誰待審核、誰是候補第幾位。

## 修好的老問題：報名名單 CSV 匯出其實是空的

這個版本新增的瀏覽器檢查（會攔下載的內容來驗）抓到一個**存在很久、但很難發現**的 bug：

- `CMCSV.stringify()` 只認「陣列列」（`[['a','b'], ['1','2']]`），但報名名單匯出傳的是「物件列」（`{姓名:'王小明', 隊伍:'A 隊'}`，這是**這個版本才加的欄位，但寫法沿用原本的**）。
- 結果：CSV 檔案下載成功、檔名正常、**打開是一堆空行**。沒有錯誤訊息、沒有例外，畫面還顯示「已匯出 N 筆報名資料」。
- 修法（兩層）：
  1. `stringify()` 現在遇到物件列會自動產生「表頭 + 資料列」（欄位順序照物件），缺的欄位留空——同一個坑以後不會再踩。
  2. 匯出改成帶上「狀態」「候補順位」兩欄。
- 驗證：瀏覽器檢查會覆寫 `URL.createObjectURL` 把 blob 攔下來，**讀出真正的 CSV 文字**，斷言表頭有「狀態」「候補順位」、內容有「已核准」與資料列數。單元測試也補了物件列的三個案例（含公式注入防護在物件列下仍生效）。

## 設計取捨（重點）

| 決定 | 理由 |
| --- | --- |
| 拖拉用 pointer 事件，不用 HTML5 drag and drop | HTML5 DnD 在行動瀏覽器基本不能用；pointer 事件桌機手機同一條路徑，且專案不用外部套件（CSP 不放寬）。 |
| 拖動時只動畫面、放手才送 API | 拖的過程中一路送 API 會產生大量請求與中間狀態；「放手＝確認」也符合直覺，失敗時再拉回真實狀態。 |
| 保留 ↑／↓，再加下拉與拖拉 | 三種操作各有適用場景（微調、遠距搬移、直覺操作）；下拉也是鍵盤使用者的唯一遠距搬移方式。 |
| 異動紀錄讀稽核日誌，不另開表 | 兩份資料一定會有一天不一致。稽核日誌本來就記了操作者與內容，直接讀＝永遠同步、也不需要新的 migration。 |
| 通知開關放在「賽事」層級，不是全域 | 不同賽事的聯絡習慣不同（有的用群組、有的靠系統通知）；放全域會逼所有人接受同一種做法。 |
| 關掉通知時**連推播訂閱都不查** | 「沒通知」與「有查但沒送」在事後追查時完全不同；連查都不查，行為最好預測，也省一次資料庫往返。 |
| migration 缺失時「一律通知」而不是「一律不通知」 | 少一個欄位不該讓既有功能（遞補通知）默默失效——通知是既有行為，寧可維持原狀。 |
| `stringify()` 支援物件列而不是只修呼叫端 | 修一處只解決今天；讓模組自己處理物件，才不會下一個呼叫端又產生空 CSV。 |

## 已知限制

- 拖拉是「按住把手拖曳」，**不支援鍵盤拖拉**（鍵盤使用者請用「第 N 位」下拉）。
- 異動紀錄固定抓最新 100 筆後再切頁（`limit` 最大 100），沒有「載入更早」的按鈕；需要更久以前的紀錄請到稽核日誌頁面篩選該賽事。
- 順位調整**不會通知**被移動的人（只有真的被遞補才通知）；關閉通知時連被遞補的人也不通知。
- 拖曳排序一次只搬一筆；沒有「多選一次搬多筆」（若之後真的需要，做法會是加勾選框再拖）。
