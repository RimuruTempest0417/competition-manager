# v2.21.0 — 候補順位的兩個實務缺口：指定遞補、手動調整順序

**發佈日期**：2026-09-26｜**類型**：P1 賽事與報名核心（Roadmap P1-2 補強）

## 為什麼要做

v2.20.0 讓候補名單能自動遞補之後，實際操作上馬上遇到兩個「規則太死」的狀況：

1. **候補第一名聯絡不到 / 不是需要的人**：自動遞補一定補第一位。但真實情況是——第一位的電話打不通、或是他的組別根本不符合這場比賽，主辦只能先「取消他」再讓系統補下一位。取消別人的報名是**破壞性**的動作（對方會收到通知、紀錄也變了），只為了「跳過他」非常不合理。
2. **需要調整整體順序**：已經繳費的、同一隊的、設備借用的，實務上就是該往前排。而 v2.20.0 的順位是「先報名先排」，**唯一的調整方式是改報名時間**——那等於偽造資料。

這一版把兩個缺口補起來，而且**不動既有的自動遞補行為**（沒調整過順位時，一切跟 v2.20.0 一樣）。

## 新增

### 1. 指定遞補（不照順位）：`POST /api/registrations/:id/promote`

管理員可以直接挑候補名單裡的**任何一位**遞補，跳過排在他前面的人。

- **被跳過的人完全不受影響**（狀態、順位、資料都不動）——這是與「先取消再遞補」最大的差別。
- 名額守門與「遞補下一位」**共用同一份純函式** `planPromotion()`：名額已滿 → `400`（不能超收）、對象不在候補名單（已核准／未錄取／不存在）→ `400`／`404`。
- 需審核的賽事，指定遞補進來的人**仍是待審核**（不會因為被指名就免審）。
- 稽核 `PROMOTE_WAITLIST`，內容寫明「指定遞補候補: 某人（第 N 順位 → 狀態，**未照順位**）」；`review_note` 記「指定遞補（原第 N 順位）」，事後看得出這不是照順序補的。
- 一般用戶 → `403`；未登入 → `401`。

### 2. 候補順位手動調整：`POST /api/competitions/:id/waitlist/reorder`

管理員送「**完整的**候補 id 順序」，後端寫入每筆的 `waitlist_order`（1 開始）。

- **少一筆、多一筆、重複 id 一律整批拒絕**（`400`），並要求重新整理：寧可拒絕，也不要寫出「少數人被默默擠到後面」的半套結果。拒絕時**不修改任何資料**（測試有驗）。
- 排序規則（純函式 `waitlistQueue()`，前後端共用）：
  1. 兩筆都手動排過 → 照 `waitlist_order`（小的在前）
  2. 只有一筆排過 → 排過的在前面
  3. 都沒有 → **先報名先排**（`created_at`，其次 `id`）
  → 因此**新報名的人一律排到最後**，不會插隊；沒被手動排過的人維持原相對順序。
- 稽核 `REORDER_WAITLIST`，內容列出新的順序（超過 8 人會截斷並標示「…等 N 人」）。
- 未執行 migration → `503` ＋ 檔名指引（見下）。

### 3. 介面（管理員的報名／隊伍視窗）

- 候補每一列：**`↑`／`↓`**（與隔壁那筆對調，第一列的 ↑、最後一列的 ↓ 停用）＋**「⬆️ 遞補」**（指定遞補這一位，會先確認「會跳過排在前面的候補」）。
- 候補區塊標題下方新增**順位來源說明**：
  - 「順位：依報名時間自動排序（可用 ⬆️⬇️ 手動調整）」
  - 「順位：管理員手動排定（新報名的人一律排到最後）」
  - 未執行 migration：「順位：依報名時間自動排序（執行 v2.21.0 migration 後可手動調整）」（此時**不顯示** ↑／↓）
- **名額已滿時每一列的「遞補」都停用**（滑過去看得到原因），區塊層級的「遞補下一位」也維持停用——後端照樣會擋，前端先講清楚避免白按。
- 「我的報名」的候補順位跟著管理員排定的順序走（同一份排序規則）。

### 4. 資料庫欄位（`migrations/2026-09-26-v2.21.0-waitlist-order.sql`）

```sql
alter table registrations add column if not exists waitlist_order integer;
```

可重複執行（`IF NOT EXISTS`），另附一個排序用索引。**未執行時**：

- 調整順位的端點回 `503` ＋ 檔名指引，**不寫入任何資料**。
- 候補順位自動退回「先報名先排」（既有行為完全不變）。
- **指定遞補仍可用**（它不需要這個欄位）。
- 前端 `canReorderWaitlist: false` → 不顯示 ↑／↓ 按鈕，並在說明文字裡講清楚。

## 設計取捨（重點）

| 決定 | 理由 |
| --- | --- |
| 另外開 `waitlist_order` 欄位，不改 `created_at` | 改報名時間是**偽造資料**：稽核、匯出、客服查詢都會看到錯的時間。排序是排序，時間是時間。 |
| 排序規則讓「沒排過的人」維持原順序、新報名排最後 | 管理員只調他關心的人，其他人的相對順序不會被攪亂；新報名的人也不能靠運氣插到前面。 |
| 送出「完整順序」而不是「把 A 移到 B 前面」 | 完整順序可以在後端一次驗證「跟我看到的名單一致」，避免兩人同時操作造成不可預期的結果（這也是拒絕時要求「重新整理」的原因）。 |
| 名單不一致就整批拒絕 | 部分套用最危險：管理員以為調好了，實際上是另一份順序。整批拒絕 + 明確原因，行為可預測。 |
| 名額守門抽成 `planPromotion()` 共用 | 「遞補下一位」與「指定遞補」若各寫一份，遲早出現「一個擋、一個不擋」。同一份純函式兩邊呼叫。 |
| 指定遞補也要通知與稽核 | 被遞補的人收到的是同一種通知（他不需要知道自己是「被指定」的）；但**稽核要寫清楚未照順位**，主辦日後查得到。 |
| 未執行 migration 時功能分兩級降級 | 指定遞補不需要新欄位 → 照常可用；順序調整需要 → `503` ＋指引。不是「整組關掉」。 |

## 已知限制

- 只能「和隔壁那筆對調」（↑／↓），沒有拖拉排序：手機上拖拉容易誤觸，而且專案不用外部套件、也不放寬 CSP。要一次大搬風時，多按幾次即可。
- 調整順位**不會通知**被移動的人（避免騷擾）；只有真的被遞補才通知。
- 順位是「管理員排定的整數」，**遞補／取消之後不會自動重新編號**（例如第 1 位被遞補後，第 2 位仍是 2）。畫面顯示的是**即時算出來的名次**，所以看到的一定是連續的 1、2、3，不會有洞。
- 沒有「順位異動歷史」頁面：目前只能從稽核日誌的 `REORDER_WAITLIST` 逐筆查看（內容有列出當時的完整順序）。
