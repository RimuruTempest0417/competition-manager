# v2.12.0 安全性檢查報告（漏洞總檢查）

- **檢查日期**：2026-09-25
- **檢查範圍**：`server.js` 全部 44 條路由、`public/js/*` 前端、`public/index.html`、資料庫存取方式、部署設定
- **檢查方式**：程式碼逐項盤點 + 對正式站的實際請求探測（未登入／低權限／錯誤權杖）+ 自動化測試（`npm test` 90 項、headless Chrome 手機實測 46 項）
- **原則**：每一項都寫出「發現 → 影響 → 處置」。已修復者附上驗證方式；刻意保留者說明原因。

## 一、本次修復的問題

### 1. 錯誤日誌寫入失敗時完全靜默（回報的 bug，已修復）

| 項目 | 內容 |
| --- | --- |
| 發現 | `logErrorToDb()` 只 `await supabase...insert()` 而**沒有檢查回傳的 `error`**。Supabase 客戶端不會因 HTTP 錯誤丟出例外，因此只要寫入失敗（欄位不存在、RLS 阻擋、連線問題），日誌就無聲無息消失，只在 console 留一行訊息（雲端部署看不到）。 |
| 影響 | 使用者看到的「系統有錯誤卻沒有寫入錯誤日誌」正是這個情況；事後無法追查。 |
| 修復 | 改為檢查 `{ error }` 並在失敗時記錄到記憶體環狀緩衝，新增 `GET /api/admin/error-logs/health` 讓後台可直接看到「日誌系統本身」的寫入失敗（錯誤日誌視窗開啟時也會顯示紅色警示）。 |
| 驗證 | 單元／整合測試 + 手機實測「日誌系統本身狀態良好時不顯示警告」；正式站以觸發真實錯誤確認寫入。 |

### 2. 13 條錯誤路徑完全沒有寫入日誌（同一 bug 的另一半，已修復）

| 項目 | 內容 |
| --- | --- |
| 發現 | 以程式掃描 45 個 `catch` 區塊，其中 13 個沒有 `logErrorToDb()`，例如 `POST /api/push/unsubscribe`、`POST /api/push/test`、`GET /api/registration-counts`、`GET /api/competitions/:id/poster`、`/api/logs/error` 自身失敗、以及 `logErrorToDb` 內部失敗。 |
| 影響 | 推播、報名人數統計、海報讀取等功能的錯誤不會留下任何紀錄。 |
| 修復 | 逐條補上日誌（並區分 `severity`：error / warn / info）；`authenticateToken` 的無效權杖也記為 `warn`。 |
| 驗證 | 整合測試斷言 `login_lockout`、`auth_invalid_token` 會自動寫入。 |

### 3. 未登入狀態下可寫入日誌／推播端點（DoS 風險，已修復）

| 項目 | 內容 |
| --- | --- |
| 發現 | `POST /api/logs/error`、`POST /api/push/unsubscribe`、`POST /api/push/test` 都不需要登入，且**沒有任何速率限制**（只有登入／註冊有）。 |
| 影響 | 任何人可用腳本灌入大量資料列，讓資料庫膨脹、後台日誌被垃圾淹沒；`/api/push/test` 還能被用來反覆觸發推播。 |
| 修復 | 新增 `allowPublicWrite()`（依 IP 的記憶體滑動視窗節流）：錯誤回報 30 次/分、取消訂閱 30 次/分、測試推播 10 次/分；並限制錯誤回報欄位長度（message 1000、stack 4000、path 300、UA 400 字元）。 |
| 驗證 | `npm test` 之使用者管理測試 + 手機實測；正式站以短時間連續請求確認會回 429。 |

### 4. 任何 403 都會把使用者強制登出（UX／可用性缺陷，已修復）

| 項目 | 內容 |
| --- | --- |
| 發現 | 前端 `customFetch()` 把 **401 與 403 一視同仁**：清掉 token、alert、`window.location.reload()`。但 403 同時是「權限不足」的正常回應（例如管理員嘗試建立管理員）。 |
| 影響 | 使用者只要碰到一次權限不足就被踢下線並重載頁面；錯誤訊息也被 alert + reload 蓋掉，看不出真正原因。 |
| 修復 | 後端：無效／過期權杖改回 **401**（語意正確：未認證）；前端：401 或訊息明確為「Token 無效／已過期」才視為登入失效，403 照常把後端訊息顯示給使用者。 |
| 驗證 | 手機實測「就算前端被繞過，後端仍會擋下提權（說明權限不足）」且不會被登出。 |

### 5. CSV 公式注入（Excel / Google Sheets，已修復）

| 項目 | 內容 |
| --- | --- |
| 發現 | `escapeCell()` 只處理引號與逗號，`=、+、-、@` 開頭的內容會被試算表當成**公式執行**（可造成資料外洩或執行外部指令，如 `=HYPERLINK(...)`、`=cmd|...`）。 |
| 影響 | 匯出賽事／報名名單／錯誤日誌成 CSV 後，用 Excel 或 Google Sheets 開啟就有風險；惡意使用者也能把 payload 藏在賽事名稱裡。 |
| 修復 | 新增 `sanitizeCell()`：危險前綴一律加上單引號（`'=1+1`），**純負數（-12.5）保持原樣**以免破壞資料；所有匯出（賽事、報名名單、錯誤日誌）都經過此函式。 |
| 驗證 | `tests/csv.test.js` 新增 2 項測試（含匯出→匯入往返仍正常）。 |

### 6. 伺服器錯誤訊息外洩資料庫細節（已修復，帳號相關端點）

| 項目 | 內容 |
| --- | --- |
| 發現 | 帳號／權限／日誌相關端點的 500 回應直接把 `err.message` 回給前端，會透露資料表與欄位名稱（PostgREST 錯誤原文）。 |
| 修復 | 這些端點改回統一的 `GENERIC_DB_ERROR` 訊息，細節仍完整寫入 `error_logs` 供管理員追查。 |
| 驗證 | 整合測試（含降級模式）與手機實測皆通過。 |

### 7. API 回應可能被快取（已修復）

| 項目 | 內容 |
| --- | --- |
| 發現 | 安全標頭中沒有針對 `/api/*` 的 `Cache-Control`。 |
| 修復 | 所有 `/api/*` 回應加上 `Cache-Control: no-store`（海報端點仍保有其 public 快取設定，因為它是公開圖片）。 |

## 二、檢查後確認「沒有問題」的項目（附驗證方式）

| 項目 | 結論 |
| --- | --- |
| **權限中間件覆蓋** | 44 條路由逐條檢視：寫入與管理類端點全部有 `requireAdmin`／`requireSuperAdmin` 或 `authenticateToken`；公開的只有讀取類（賽事列表、人數、公開設定、推播公鑰、海報）與登入／註冊／錯誤回報。 |
| **水平越權（IDOR）** | `DELETE /api/registrations/:id` 有擁有者檢查（非本人需管理員）；`GET /api/competitions/:id/registrations` 對非管理員強制只查自己的 `user_id`；隊伍編排端點為管理員以上。 |
| **Mass assignment** | 建立／編輯賽事、報名、建立帳號都採「逐欄取用 + `sanitizeInput()`／`cleanText()`」而非把 `req.body` 直接寫入；註冊端點的角色**硬寫為 `user`**，無法自行提權。 |
| **提權（角色階梯）** | 新增的階梯規則：管理員只能建立 `user`／`test`；超級管理員可再建立 `admin`；角色調整僅網站擁有者。已由 12 項整合測試與手機實測（前端繞過仍被後端擋下）驗證。 |
| **PostgREST／SQL 注入** | 沒有任何使用者輸入被拼進 `.or()` / `order()`；錯誤日誌搜尋參數會先移除 `% , ( ) *` 等語法字元並限制長度；`sort` 查詢參數不存在（無白名單需求）。 |
| **XSS** | 無 inline script／inline style，CSP 維持 `script-src 'self'`、`style-src 'self'`；所有插入 DOM 的資料都經 `escapeHtml()`；頭像／海報以 `img-src 'self' data:` 白名單處理。 |
| **JWT** | 12 小時到期；`requireRole` 每次請求都回資料庫比對帳號與角色（角色被改即失效，不用等 token 過期）；未設定 `JWT_SECRET` 時 production 拒絕啟動（已有測試）。 |
| **密碼儲存** | scrypt 加鹽雜湊（`hashPassword()`），僅相容舊明碼驗證；登入失敗訊息不區分帳號不存在或密碼錯誤。 |
| **暴力破解** | 登入連續失敗 5 次鎖定 15 分鐘（429）；註冊同一 IP 每小時 5 次；新增帳號的密碼格式驗證。 |
| **自動推播端點** | v2.11.1 已修正：production 未設 `CRON_SECRET` 回 503、權杖錯誤回 401（`timingSafeEqual`）。 |
| **機密外洩** | `.env` 未被提交；程式碼內沒有硬編碼金鑰；前端完全不直接呼叫 Supabase（僅透過自家 API）。提交前以 `eyJhbGciOi`、`service_role`、`SUPABASE_KEY=`、`VAPID_PRIVATE` 掃描。 |
| **安全標頭** | CSP、X-Frame-Options: DENY、X-Content-Type-Options: nosniff、HSTS、Referrer-Policy 齊備；`X-Powered-By` 已關閉。 |
| **檔案上傳** | 海報只接受 JPG／PNG／WebP 的 data URL（`parseImageDataUrl()` 驗證魔數），上限 3MB，需管理員權限，存 DB 後由自家端點供應（無儲存桶、不放寬 CSP）。 |

## 三、刻意保留的限制（已評估、風險可接受，但應知情）

| 項目 | 說明與建議 |
| --- | --- |
| **資料庫使用 anon key 且未開 RLS** | 目前是既有架構決定：`SUPABASE_KEY` 是 anon key，若開啟 RLS 又沒有 policy 會讓寫入全部失敗（實測錯誤碼 42501）。此金鑰**只存在伺服器端**、前端從不直連，但只要金鑰外流就等於全資料庫可讀寫。**建議**：日後改用 `service_role` key 並開啟 RLS + policy。 |
| **公開報名名單的可見範圍** | `GET /api/competitions/:id/teams` 讓任何登入者看到該場的隊伍與成員帳號（設計上方便參賽者確認隊伍）。屬刻意設計，若需更嚴謹可限制為「該場參賽者」。 |
| **部分非帳號端點仍回傳原始錯誤訊息** | 例如賽事／報名／隊伍的 500 回應（需登入或管理員權限才看得到）。優先度較低，仍建議後續一併改為通用訊息（細節已寫入 `error_logs`）。 |
| **記憶體式節流與登入鎖定** | 部署在 Vercel serverless，多實例時各自的計數不共享，重啟即歸零。足以阻擋單一來源的腳本濫用，但**無法**阻擋分散式攻擊。**建議**：如需更嚴格，改用資料庫或 Redis 記錄失敗次數。 |
| **登入鎖定可被用來鎖住他人帳號** | 以帳號為鍵的鎖定（5 次／15 分鐘）可被有心人用來對特定帳號做阻斷。目前站台規模與使用情境可接受；若對外開放建議改為「帳號 + IP」雙重計數。 |
| **無 Email 驗證／兩步驟驗證** | 帳號由管理員建立或邀請碼註冊，沒有信箱驗證與 2FA。 |
| **錯誤日誌含有使用者輸入** | 日誌會保存 UA、路徑與訊息內容（可能含使用者輸入片段）。已限制長度並只開放給超級管理員以上檢視，並提供「清理 N 天前」功能。 |
