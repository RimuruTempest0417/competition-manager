## 二、後端、基礎設施與安全

| 底層架構 | Express RESTful API 基礎建設 | 已完成 | GET / POST / PUT / DELETE 端點與 JSON 資料處理、錯誤處理中間件。 |
| 雲端基礎設施 | Supabase (PostgreSQL) 雲端資料庫 | 已完成 | 取代 SQLite，資料跨裝置永久保存。 |

| 自動化維運 | 過期數據自動排查 | 進行中 | `push_log` 已可去重與清理；賽事歸檔／過期清理尚未實作，但**排程基礎設施已具備**，可直接掛在同一支 cron。 |
| 外部數據接入 | 自動化網路爬蟲（Scraper Service) | **未開始** | 需背景爬蟲服務與目標網站授權評估。 |

| 權限與驗證 | 後端 API 權限中間件 | 已完成 (v2.9.0 擴充) | `authenticateToken` + `requireAdmin` / `requireSuperAdmin`（`ADMIN_ROLES`／`SUPER_ADMIN_ROLES` 白名單），所有寫入端點皆有把關。 |

| 安全標頭 | CSP / X-Frame-Options / nosniff / HSTS / Referrer-Policy | 已完成 | CSP 維持 `script-src 'self'`、`style-src 'self'`、`img-src 'self' data: blob:`——**v2.10.0 的手動海報以同源端點提供，因此沒有放寬任何 CSP 指令**、也未引入任何 CDN。 |
| 前端 | 無框架、原生 JS + 本地 Tailwind | 已完成 | 不使用任何 CDN 或第三方前端套件（符合嚴格 CSP）。 |

## 六、已知限制（誠實說明）

1. **必須執行 v2.10.0 migration**：目前已執行的 v2.9.0 migration 開啟了新資料表的 RLS 卻沒有 policy，anon key 寫入會被拒（實測錯誤碼 `42501`）——註冊、報名、隊伍、推播訂閱全部會失敗。執行 `2026-09-24-v2.10.0-poster-and-push.sql` 即可修好。
2. **資料庫金鑰等級**：目前使用 anon key（只存在伺服器端）。要更嚴謹應改用 `service_role` key + 開啟 RLS 與 policy。
3. **推播的兩個前提**：需要 HTTPS（Vercel 已提供）與使用者允許通知權限；iOS Safari 需將網站「加入主畫面」才能接收推播。
4. **推播檢查頻率**：伺服器端為 Vercel Cron **每日一次**（Hobby 方案限制）；開賽前 24 小時的提醒因此以「每日」為粒度。網頁開啟時的本機檢查仍為每 5 分鐘一次。
5. **電子郵件通知尚未實作**：需要外部寄信服務帳號。
6. **Realtime 即時同步尚未實作**：與「前端不直接連資料庫」的現行架構衝突。
7. **自動化爬蟲尚未實作**。
