## 一、營運儀表板出現黃色警告

**你看到的**：

> 以下區塊暫時讀不到（不影響其他數字）：push (column push_log.created_at does not exist)

**原因**：儀表板的統計查詢讀 `push_log` 時，select 與排序都用了 `created_at`，
但**這張表的時間欄位是 `sent_at`**（v3.1.1 修 migration 時發現的同一個欄位錯誤，
這次是在程式碼裡）。而且那個欄位其實**從來沒有被用到**——統計只加總 `sent_count` 與 `failed_count`。

**修正**：select 只留真正需要的兩個計數欄位，排序改用 `sent_at`。儀表板的「推播成功率」恢復正常。

**為什麼測試沒抓到**：測試用的假資料庫替身把 `push_log` 寫成有 `created_at`（跟真實資料庫不一樣），
所以「查了不存在的欄位」被放過。已把替身改成跟真實欄位一致，並在單元測試與正式站煙霧測試
都加上「**不得有任何讀不到的區塊**」斷言——以後同類問題會在測試階段就紅燈。

## 二、刪除帳號送出兩次請求

**原因**：`#adminList`（帳號清單）被綁了**兩個** click 處理器：一個是舊版遺留的監聽器，
一個是後來改寫的統一處理器，兩個都會呼叫 `deleteAdmin`。所以點一次「刪除」會：

1. 跳兩次確認對話框
2. 送出兩個 DELETE：第一個成功，第二個回 404「找不到該帳號」→ 出現「刪除失敗」提示
3. 稽核日誌留下**兩筆** `DELETE_USER`

**修正**：

- 移除舊版遺留的監聽器（保留統一處理器，功能完全等價）。
- 在 `deleteAdmin` 加上**防連點守衛**：同一個帳號在請求完成前再次點擊會被忽略（連點兩次也只送一次）。
- 順手修掉同類問題：`openAdminModal()` 每次打開都重綁「重新整理」按鈕（開兩次就會送兩個請求），
  改為只綁一次。
