# v3.5.2 — 驗證流程不再製造假錯誤日誌（8.6 ③）

**一句話**：讓自動化檢查流量能「表明身分」——伺服器驗簽通過就不把那些**預期中的**拒絕行為寫進
`error_logs`，回覆行為完全不變。正式站 33 筆錯誤日誌裡有 **30 筆（91%）** 是檢查自己造成的，本版把它歸零。

## 證據（先量測，不靠想像）

2026-09-26 讀回正式站 `GET /api/admin/error-logs?limit=200`：

| 觀察 | 數字 |
|---|---|
| 錯誤日誌總筆數 | **33** |
| 其中 User-Agent 是 `node`／`curl`（＝自動化流量） | **30（91%）** |
| 明細 | `malformed_json_body` **29**（全在 `/api/auth/login`）、`auth_invalid_token` **2** |
| 真正的系統錯誤 | 2 筆（`unhandled_server_error`、`js_runtime_issue`） |

`malformed_json_body` 的時間範圍 2026-09-25 13:58 → 2026-09-26 15:50（UTC）——正好對應每次跑
`npm run check:prod` 的「壞 JSON 要回 400」那一步（**跑一次多一筆**，近 24 小時就有 23 筆）。
後果不只是數字難看：首頁提示橫幅與 `npm run triage` 的巡檢清單被自己的測試灌水，真正的問題被稀釋。

## 改了什麼

### 1. 檢查流量表明身分：`X-CM-Self-Test`

`tests/browser/prod-smoke.js` 現在對**所有**打向正式站的請求都帶這個標頭：

```
X-CM-Self-Test: <用 JWT_SECRET 簽的短效權杖，payload = { purpose: 'self_test' }>
```

伺服器（`isSelfTestRequest()`）驗簽通過 → **不寫入** `error_logs`，但**回應行為完全不變**
（該 400 還是 400、該 401 還是 401、該擋的權限一樣擋）。

**為什麼用 `JWT_SECRET` 而不是固定字串或新環境變數**：

- 固定字串任何人都能冒充，等於送給攻擊者一個「讓自己不被記錄」的開關。
- 用 `JWT_SECRET` 簽**不需要新增任何環境變數**（本機 `.env` 與 Vercel 都已經有了），
  而且能拿到 `JWT_SECRET` 的人本來就能簽出管理員權杖，不因此多任何權限。
- 沒帶、亂帶、簽章不對 → **照常記錄**（fail-safe：寧可多記，不可漏記）。
  這三種情況都有測試釘住。

### 2. 順序很重要：自檢流量不佔用「日誌節流」額度

`authenticateToken` 對無效權杖本來有「同 IP 每分鐘最多記一筆」的防灌爆機制。
若先問節流再判斷標記，**一次 `check:prod` 就會把該 IP 的額度用掉**，讓緊接而來的真實權杖失敗被靜默吞掉。
現在順序是：自檢流量 → 直接不記、不佔額度；其餘 → 照原本的節流與記錄。
（這是寫測試時才浮出來的：對照組「沒有標記的無效權杖」第一版竟然沒被記錄。）

### 3. 可觀測：健康端點回報略過筆數

`GET /api/admin/error-logs/health` 新增 `self_test_skipped`（本實例累計略過幾筆）。
檢查腳本據此證明「標記真的被認得」，而不是「剛好什麼都沒記」。

### 4. `check:prod` 自己驗這一件事（第 6 節）

煙霧測試最後增加兩個斷言：

1. `self_test_skipped >= 1`——標記生效。
2. 列出最近 100 筆錯誤日誌，**本次執行期間（`RUN_STARTED_AT` 之後）、UA 為 node／curl 的筆數必須是 0**
   ——檢查沒有在正式站留下任何假錯誤日誌。

也就是說：這個修正**由每次發版的正式站檢查自動守門**，不需要有人記得去查。

## 順手修掉一個檢查腳本的邊界競態（不是本版改壞的）

`tests/browser/competition-state-check.js` 的「點『進行中』只留下進行中的賽事」把預期寫死成 `603`，
但種子資料 `606`（馬上要開放的賽事）的報名開始時間是「執行當下 +30 秒」——檢查跑得慢一點，
606 就會在檢查途中翻面，造成**間歇性假失敗**（2026-09-26 23:59 實際發生一次）。

- 先用 `git worktree add /tmp/cm-351 HEAD`（v3.5.1 程式碼）跑同一支檢查：**30/30 通過**，
  同一份程式碼在當前版本重跑兩次也是 30/30 → 確認與本版改動無關，是檢查自己的時間依賴。
- 修法依專案既有原則「**測試要跟伺服器要權威狀態，不要自己寫死**」：
  先打 `/api/competitions` 取得 `state === 'ongoing'` 的 id 集合，再等畫面收斂到同一個集合。
- **RED 驗證**：故意把預期多加一個 id（`601`）→ 該檢查 exit 1（`等待逾時 ... === "601,603"`）；
  還原後 30/30、exit 0。證明這條斷言不是「改不改都通過」。

## 已知限制（誠實說明）

- 這**不是**「讓錯誤日誌變好看」的粉飾：只有簽章正確的流量會被略過，攻擊者偽造不了；
  真實的伺服器錯誤與一般使用者的壞請求一律照記。
- 舊的 29 筆 `malformed_json_body` 仍在資料庫裡（本版不會刪除歷史；它們已被巡檢標記為已處理，
  且不會再增加）。要清掉得用「🧹 清理」（依保留天數）或直接在資料庫刪除——本版刻意不做，避免動歷史資料。
- 標頭只由煙霧測試使用；其他檢查（訪客視角、線上樣式）本來就只讀，不會產生日誌。
