# v2.20.0 — 報名審核與候補名單（額滿自動進候補、有人取消自動遞補並通知）

**發佈日期**：2026-09-26｜**類型**：P1 賽事與報名核心（Roadmap P1-2）

## 為什麼要做

v2.19.0 把「能不能報名」交給後端算之後，剩下的最後一塊是**報名之後**的事。真實的比賽有三種常見需求，舊版一個都做不到：

1. **要審核**：社團比賽常常要先確認身分／組別，不是報了就算。
2. **會額滿**：名額滿了以後，舊版只能讓大家吃「名額已滿」的閉門羹，主辦只能自己用 LINE 記候補名單。
3. **有人會取消**：取消之後空出來的名額，舊版要管理員自己記得去通知下一個人——十之八九會忘。

這一版把三件事一起做完，而且**規則寫在跟 v2.19.0 同一份共用模組裡**（`public/js/competition-state.js`），前端顯示、後端判定、限制名額，全部同一套。

## 名額規則（唯一真實來源）

| 狀態 | 中文 | 佔不佔名額 |
| --- | --- | --- |
| `confirmed` 已核准 | 已核准 | ✅ 佔 |
| `pending` 待審核 | 待審核 | ✅ 佔（避免「先卡位再慢慢審」造成超收） |
| `waitlisted` 候補 | 候補 第 N 位 | ❌ 不佔 |
| `rejected` 未錄取 | 未錄取 | ❌ 不佔 |

- **佔名額＝已核准＋待審核**；候補不佔名額，所以「額滿」之後仍可以無限排候補。
- 一場賽事有兩個開關（存在 `competitions`）：**`requires_approval` 報名需審核**、**`waitlist_enabled` 額滿開放候補**。兩者可獨立開啟，四種組合都測過。
- 報名時的行為由這兩個開關決定：
  - 名額還有 → 需審核就寫 `pending`，不需審核就寫 `confirmed`。
  - 名額已滿＋開放候補 → 寫 `waitlisted`，並回應候補順位（「已排入候補（第 3 位）」）。
  - 名額已滿＋沒開候補 → `400`「名額已滿」。
  - 已經報名過（含正在候補）→ `409`，不能重複報名。

## 新增

### 1. 報名審核（`POST /api/registrations/:id/review`）

管理員以上可以核准或拒絕一筆報名，**拒絕可以寫原因**（`note`，會存進 `registrations.review_note` 並寫入稽核）。

- 核准 → `confirmed`；拒絕 → `rejected`。兩者都記錄 `reviewed_at`／`reviewed_by`（誰審的）。
- 兩種結果都會**推播通知報名者**（標題「報名審核結果」），並在 `push_log` 留一筆 `review_result`。
- 名額守門：**核准時如果名額已滿會回 400**（不能靠核准超收）。
- 稽核：`REGISTER_APPROVED`（核准報名（審核））、`REGISTER_REJECTED`（拒絕報名（審核））。

### 2. 候補名單與自動遞補

- 候補有**明確順位**（先報名先排，`waitlist_position`），名單與我的報名都看得到。
- **有人取消（或管理員取消、或把已核准的人改成拒絕）讓出名額時，第一位候補自動遞補**：
  - 遞補後的狀態＝該賽事「需審核就 `pending`、不需審核就 `confirmed`」（不會讓需審核的賽事因為遞補而繞過審核）。
  - 立刻**推播通知**被遞補的人（「你已從候補遞補為已核准」），`push_log` 記 `waitlist_promoted`。
  - 稽核：`AUTO_PROMOTE_WAITLIST`（自動遞補候補），內容寫明「誰遞補、第幾順位、因為誰取消」。
- **手動遞補**：`POST /api/competitions/:id/registrations/promote`，介面上有「⬆️ 遞補下一位」。名額已滿時按鈕停用（並說明原因），後端也會擋（400 名額已滿）。稽核：`PROMOTE_WAITLIST`。

### 3. 人數統計一律以「佔名額」為準

`GET /api/registration-counts` 與賽事卡片的「N / M 人」全部改成 **已核准＋待審核**，並另外提供候補人數：

```json
{ "counts": { "501": 3 }, "waitlist": { "501": 2 }, "total": 3 }
```

卡片會顯示「🕒 額滿，報名排候補（已有 2 人候補）」與「⏳ 報名需審核」提示；額滿可候補時報名按鈕寫「📝 報名（排候補）」，送出前先說明會排到第幾位。

### 4. 管理員的審核區塊（報名／隊伍視窗）

打開賽事的「報名／隊伍」視窗，最上面多了現況統計與兩個區塊：

- 統計列：`佔名額 2 / 3 人｜已核准 0｜待審核 2｜候補 0｜⏳ 本賽事需審核｜🕒 開放候補（取消自動遞補）`。
- **⏳ 待審核**：每個人一列，右邊「✅ 核准」「❌ 拒絕」；拒絕會問原因。
- **🕒 候補名單**：顯示第幾順位、候補時間，右上「⬆️ 遞補下一位」（沒名額或沒候補時停用並提示）。
- **未編排報名者**只剩「已核准」的人——待審核或候補的人**不能被編進隊伍**（`POST /api/teams/:id/members` 會擋，避免審核前就先佔位）。

### 5. 我的報名顯示狀態

`GET /api/my/registrations` 每筆帶 `status`／`status_label`／`waitlist_position`／`review_note`／`can_cancel`：使用者看得到自己「待審核」「候補 第 3 位」「未錄取（原因）」。未錄取與被取消的報名不再顯示取消按鈕。

### 6. 資料庫欄位（`migrations/2026-09-26-v2.20.0-registration-review.sql`）

全部 `ADD COLUMN IF NOT EXISTS`／`ENABLE RLS`，**可重複執行**：

- `competitions.requires_approval`、`competitions.waitlist_enabled`
- `registrations.status`（`pending`／`confirmed`／`waitlisted`／`rejected`）
- `registrations.reviewed_at`、`reviewed_by`、`review_note`

## 設計取捨（重點）

| 決定 | 理由 |
| --- | --- |
| 規則寫在共用模組，不重寫一份 | 沿用 v2.19.0 的教訓：兩份規則＝兩份答案＝畫面說可以、送出被拒。 |
| **待審核佔名額** | 否則「先送先贏」：名額 10 的賽事可能收到 200 筆待審核，核准完才發現爆掉。要收多少待審核，由名額決定。 |
| 候補**不佔**名額 | 候補本來就是「排隊等名額」，不該吃掉名額。額滿後仍可持續收候補，主辦才有人可遞補。 |
| 遞補後仍需審核（若該賽事需審核） | 遞補是「輪到你被審」，不是「免審」。若遞補直接變已核准，等於繞過審核制度。 |
| 遞補用「取消當下立刻決定」而非背景排程 | 沒有排程就沒有「跑之前名額空著」的空窗；也不需要維護排程失敗。遞補失敗**不影響取消**（取消已生效），錯誤另外記錄。 |
| 抽掉「自動遞補」以外的自動化 | 不自動取消未繳費、不自動砍人——這一版只做「讓出名額 → 補上一位」，其餘留給管理員。 |
| 沿用「先探測欄位、沒有就不帶」 | migration 沒跑時，審核／候補功能**整組優雅停用**：報名照舊直接核准、審核與遞補端點回 503 並附指引、賽事表單不會寫入不存在的欄位，其他功能完全不受影響。 |
| 前端開關與名單都靠後端回報 `schema_ready` | 介面會誠實寫「資料庫尚未執行 v2.20.0 migration：報名審核與候補功能目前停用」，而不是顯示空名單假裝沒人報名。 |

## 順手修掉的問題

- **`regWaitlistCounts` 沒有宣告**（`let` 漏掉）：`regWaitlistCounts is not defined`，會讓整個賽事列表渲染失敗（畫面顯示「無法載入比賽資料」）。`node --check` 抓不到這種錯，是瀏覽器檢查抓到的。
- **`setTeamMsg` 參數順序寫反**：函式是 `(message, type)`，新程式碼寫成 `setTeamMsg('success', 訊息)` → 介面只顯示字串「success」。已修正（含兩處 catch）。

## 已知限制

- **遞補以「報名建立的先後」排序**（`created_at`），不是「誰先進候補」。對「先報名但被拒絕→重新報名」的人來說順位會往後，實務上可接受（也比較不容易被操作順位）。
- **不會通知被拒絕的人以外的人**：目前沒有「候補還差幾位」的公開資訊（只有人數統計），避免讓人排隊時被數字影響。
- 推播是靠瀏覽器訂閱（Web Push）；**沒有訂閱的人收不到通知**，介面會誠實回報「對方沒有推播訂閱，未通知」，但不會自動改用 Email（Email 通知已從 Roadmap 移除）。
- 尚未支援「同時保留多筆候補順位的手動調整」（管理員只能遞補下一位，不能指定某人）。
