# v3.5.3 — 修正 v3.5.2 的一項斷言：serverless 多實例下不能用記憶體計數器

**一句話**：v3.5.2 讓檢查流量不寫錯誤日誌（正式站實測有效：33 筆 → 33 筆，完全沒增加），
但它在 `check:prod` 加的那項「`self_test_skipped >= 1`」斷言**自己是錯的**——本版改成純行為驗證。

## 發生了什麼

v3.5.2 上線後跑 `npm run check:prod`：

```
【6】自動化檢查不留下假錯誤日誌
  ❌ 伺服器認得檢查流量標記（已略過 0 筆錯誤日誌） → self_test_skipped=0
══════ 正式站煙霧測試：96 通過 / 1 失敗 ══════
```

但**決定性證據顯示功能是正常的**：同一趟檢查前後讀回正式站錯誤日誌
`total / 自動化來源 / malformed_json_body`＝**33 / 30 / 29 → 33 / 30 / 29**（完全沒變；
修正前每跑一次會多約 30 筆）。

## 根因

`self_test_skipped` 是**單一實例記憶體內的累計**（存在 `serverState`）。Vercel 是 serverless 多實例環境，
讀 health 的那個請求很可能落到**另一個實例**（沒處理過標記流量的那個）→ 讀到 0。
**計數器不是可靠的觀測方式**，這是我自己選錯的斷言。

（同時也再次印證：只有把「遠端真實狀態」讀回來比對，才看得出來是斷言錯而不是功能錯。）

## 修法

`tests/browser/prod-smoke.js` 第 6 節改成**行為驗證**，不依賴任何記憶體計數：

1. 先讀 `/api/admin/error-logs?limit=1` 記下 `total`。
2. **當場再送兩個標記過的預期錯誤請求**：一次壞 JSON（本來會寫 `malformed_json_body`）、
   一次無效權杖（本來會寫 `auth_invalid_token`），等 1.5 秒（`logErrorToDb` 非阻塞）。
3. 重新列出日誌，斷言：① 探測之後**沒有**任何 node／curl 來源的新紀錄；
   ② `total` **沒有增加**（印出「33 → 33」這種可對帳的數字）。
4. `self_test_skipped` 改為資訊列（`ℹ️ … 僅供參考`），並在程式碼註解寫明它為什麼不能當斷言。

## 順手修掉另一個「每天凌晨必紅」的既有檢查（同樣不是本版改壞的）

`tests/ops-stats-api.test.js` 的「報名統計…趨勢長度固定」在 2026-09-27 00:15 失敗，
先用 `git worktree add /tmp/cm-352 1a0931b`（**上一版已發佈的程式碼**）跑同一支測試重現 → 確認與本版無關。

- **根因**：最後一行斷言 `trend[13].date <= new Date().toISOString().slice(0,10)` 拿 **UTC** 日期
  去比伺服器算的**本地**日期。澳門（UTC+8）時間 **00:00–08:00** 之間 UTC 還停在昨天 →
  本地今天 > UTC 今天 → **每天凌晨固定假失敗**。
- **修法**：改用與伺服器**共用同一份** `public/js/stats.js` 算期望值
  （`CMStats.trendByDay([], { days: 14, now: new Date() })[13].date`），並把 `<=` 收緊成 `===`。
  兩邊永遠同一個時區定義，也不會因為演算法改動而漂移。
- **RED 驗證**：在 00:05 把斷言還原成 UTC 比較 → 9 通過 / **1 失敗**；改回 → 10 通過 / 0 失敗。

## 教訓（已寫進 skill）

**① 在 serverless／多實例環境，任何「行程內計數器」都不能用來證明跨請求的行為**；
**② 比較日期時絕不要一邊用 UTC、一邊用本地時間**（澳門 00:00–08:00 必紅）；
**③ 檢查腳本裡的相對時間（+N 天／+30 秒）是假失敗的溫床——預期值要向伺服器要權威來源**。
要驗證遠端系統的行為，就用遠端可對帳的事實：改動前後讀同一個總數、看有沒有新增，
而不是問「你剛才算到幾筆」。
