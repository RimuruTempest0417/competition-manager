# v2.16.0 — 稽核日誌強化（篩選、分頁、匯出、保留天數）

發佈日期：2026-09-26

## 一、為什麼要做

稽核紀錄（audit_logs）從 v2.4.0 就開始寫，登入、改賽事、編排隊伍、發推播都留著——但介面上**只能看最近 100 筆**，
而且不能篩選、不能匯出。也就是說：資料一直在累積，真要追查時卻幾乎用不了。

這一版把它變成真正能用的工具。

## 二、做了什麼

| 功能 | 說明 |
|---|---|
| 篩選 | 使用者、動作（下拉，**含中文說明**）、時間區間（起訖日期）、關鍵字（比對使用者／動作／目標／詳情，大小寫不敏感） |
| 分頁 | 每頁 100 筆，可翻新舊頁；顯示目前範圍與總數。**拿不到精確總數時老實顯示「可能還有更多」，不假造數字** |
| 匯出 CSV | 套用同一組篩選條件、含中文動作說明欄、帶 BOM（Excel 開中文不亂碼）、沿用試算表公式注入防護（`=`／`+`／`-`／`@` 前置消歧） |
| 保留天數清理 | 可「先預覽會刪幾筆」再確認；天數下限 **30 天**（避免手誤刪光）；**預設不自動刪任何東西** |
| 自動清理（選用） | 只有設了環境變數 `AUDIT_RETENTION_DAYS`（≥30）才會由每日排程順便清理；沒設就完全不動資料 |
| 可追溯 | 匯出與清理本身都留稽核紀錄（`EXPORT_AUDIT_LOGS`／`PURGE_AUDIT_LOGS`），清理另留一筆**警告級**錯誤日誌 |

設計上刻意保守的兩個決定：

1. **不預設自動刪除**。稽核紀錄是事後追查用的證據，不該因為部署了新版本就開始默默消失。要開就明示一個環境變數。
2. **天數下限 30 天**。清理是不可逆的，留一道「數字明顯不合理就拒絕」的防線（有測試覆蓋）。

## 三、實作上的兩個細節（給未來的自己）

- **分頁一律從第 0 筆取到「本頁結尾 + 1」再自己切**，而不是把 offset 丟給資料庫。
  原因：正式站的 PostgREST 會依 `range` 回傳，但測試用的假 Supabase 回全部——兩種環境行為不同就會出現
  「測試說 has_more=false，線上卻還有資料」這種鬼故事。自己在 JS 切一刀，兩種環境就完全一致。
- **關鍵字搜尋在伺服器端以「最近 1000 筆」為範圍做 JS 篩選**（畫面上會標示），
  因為 PostgREST 的 `or()` 在測試替身不支援，而稽核量不大，固定視窗的確定性比「號稱全表搜尋」實際得多。

稽核日誌介面的瀏覽器檢查實際做了：開啟日誌 → 第一頁 100 筆 → 翻到第二頁再翻回 → 動作下拉中文標籤 →
動作篩選（75 筆全部符合）→ 關鍵字查詢（只剩符合的）→ 清除條件 → **實際攔下匯出的 Blob 檢查 CSV 內容**
（表頭、行數、公式消歧）→ 清理預覽（顯示將刪 1 筆、此時還沒刪）→ 確認刪除（舊的消失、新的留著、列表自動重載）
→ 全程無前端例外。
