# v2.19.0 — 賽事狀態機（含自動切換）＋ 稽核紀錄補齊

**發佈日期**：2026-09-26｜**類型**：P1 賽事與報名核心（Roadmap P1-1）＋ 回應「確保以上內容均有記錄 logs」

## 為什麼要做

在這版之前，一場賽事「能不能報名」是**使用者端自己算**的：前端拿 `date`／`is_registration_open`／`registration_deadline` 推論，後端在送出報名時另外再算一次。兩邊各有一套規則，就會出現兩種最糟的情況：

1. **畫面說可以報名，送出卻被拒**（或反過來，按鈕鎖住但其實還能報名）。
2. **該自動切換的狀態不會切**：報名時間到了、賽事開始了、結束了，畫面還是同一個樣子——只能靠管理員手動去改 `is_registration_open`。

所以這一版把「狀態」變成後端唯一的事實，前端只負責顯示。

## 新增

### 1. 一組正式定義的賽事狀態（後端即時判定）

| 狀態 | 什麼時候 | 可以報名 |
| --- | --- | --- |
| `registration_open` 報名中 | 已經到報名開始時間（或沒限制）且還沒截止，賽事也還沒開始 | ✅ |
| `registration_upcoming` 尚未開放報名 | 還沒到 `registration_start_at` | ❌（顯示「報名將於 … 開始」） |
| `registration_closed` 報名已截止 | 過了 `registration_end_at`／舊欄位 `registration_deadline`，或管理員手動關閉報名 | ❌（顯示「報名已於 … 截止」／「未開放報名」） |
| `ongoing` 進行中 | 已到賽事開始時間、還沒到結束時間 | ❌（顯示「此賽事已開始，報名已截止」） |
| `finished` 已結束 | 過了結束時間 | ❌（顯示「此賽事已結束」） |
| `unscheduled` 日期未定 | 沒有填日期 | ✅（沿用舊行為） |
| `deleted` 已刪除／`missing` 不存在 | 軟刪除或找不到 | ❌ |

「**自動切換**」不需要任何排程：狀態是**每次讀取時用當下時間算出來的**，所以時間一到，重新載入（或下次進站）就換狀態。時間軸也處理了兩個容易錯的邊界：

- **單日賽事沒有 `end_date` 時，結束時間是「當天 23:59:59」**，不是「開始時間」——否則 09:00 開始的比賽在 09:01 就被判成已結束。
- **結束時間那一刻起算已結束／開始時間那一秒起算進行中**，兩種邊界都有測試（也包含「30 秒前剛截止」「30 秒後才開始」的真實瀏覽器驗證）。

### 2. 前後端共用的唯一真實來源

新檔案 `public/js/competition-state.js`（UMD）：後端 `require()`、前端用 `<script>` 載入，**同一份規則**。前端再也不會算出跟後端不同的答案。

- 後端：`/api/competitions` 每一筆都附上 `state`／`state_label`／`state_detail`／`can_register`／`registration_reason`／`is_full`；`?state=ongoing,finished` 可只取指定狀態。
- 前端：卡片徽章、狀態篩選列（含各狀態數量）、報名按鈕（鎖住時直接寫出原因）、表單的**即時狀態預覽**——全部用同一份規則算。

### 3. 報名開始／截止時間（時間欄位，不是只有日期）

表單新增「報名開始」「報名截止」（`datetime-local`）。後端會驗證時間字串、寫入 `registration_start_at`／`registration_end_at`，**並自動同步舊欄位 `registration_deadline`**（舊前端與既有查詢照樣可用）。清空欄位也會真的把資料庫欄位清成 null。

### 4. 稽核紀錄補齊（回應「請確保以上內容均有記錄 logs」）

| 補上的紀錄 | 說明 |
| --- | --- |
| `LOGOUT` | 新增 `POST /api/auth/logout`，登出**真的寫一筆稽核**（原本登出只清前端狀態，日誌裡看不到任何痕跡）。前端 `handleLogout` 改為先呼叫 API。 |
| `SEND_PUSH` | 實際發送推播時寫入稽核（原本只有「設定變更」有紀錄，看不出誰真的發過推播）。 |
| 動作標籤補齊 | `AUDIT_ACTION_LABELS` 與程式實際會寫的動作對齊，稽核日誌的動作下拉選單不再有「查了永遠 0 筆」的選項。 |
| **守門測試** | 新增 `tests/audit-actions.test.js`：比對「選單宣告的動作」＝「程式 `logAudit` 實際會寫的動作」。這種不一致原本**不會有任何錯誤訊息**——選單多一個動作就是永遠查不到、程式多寫一個動作就是選單裡找不到。測試已用「故意加一個假的動作」驗證過真的會轉紅。 |
| 端到端驗證 | `tests/audit-actions-api.test.js`、`tests/audit-logout-api.test.js`：登出與實際發送推播後，**回查稽核日誌真的查得到那一筆**。 |

## 設計取捨（重點）

| 決定 | 理由 |
| --- | --- |
| 狀態由**後端**算，前端不算 | 前端算 ＝ 兩份規則 ＝ 一定會走鐘。前端只顯示後端給的狀態，並用同一份模組做「預覽」。 |
| **不用排程**改狀態 | 狀態是時間的函數，讀取時算就好。排程會有「跑之前狀態是錯的」空窗，還要維護排程失敗。 |
| 名額額滿不算一種狀態 | 狀態仍是「報名中」（時間上確實還能報名），額滿用 `can_register: false` ＋ `is_full` 表示。少一種狀態就少一組組合。 |
| 舊欄位 `registration_deadline` 保留且自動同步 | 舊前端、舊資料（含既有 9 場賽事）不用一起改；新舊兩份資料不會互相矛盾。 |
| 不合法時間字串**丟棄**而不是報錯 | 只有這兩個欄位壞掉，不該讓整場賽事存不進去；存成 null 由狀態機自然退化為「沒有報名截止限制」。 |
| 欄位不存在時回 `registration_window_saved:false` ＋ `warning` | 沿用「先探測欄位、沒有就不帶」的慣例。寧可誠實說「時間沒存進去」，不要讓使用者以為存好了。 |
| 狀態色票沿用既有 `--cm-*` 變數 | 深色模式、列印、三態主題都自動跟著走，不需另寫一套顏色。 |

## 一併修掉的舊問題（順手、非本版主題）

- **`custom.css` 缺 11 個 class 規則**（`bg-amber-200`、`bg-rose-600`、`border-rose-200`、`hover:bg-rose-700`、`text-amber-900`、`text-emerald-800`…）：這些 class 早就寫在 HTML／JS 裡，但 CSS 沒有規則 → **靜默失效**（例如玫瑰色按鈕其實沒有底色）。已補齊並加上深色模式的色票。
- **`class-coverage.py` 誤判**：把 `var(--x, 有預設值)` 這種「有 fallback 的可選變數」當成未定義。已修正判定（fallback 不算未定義），檢查才能維持全綠。
- **賽事狀態機的單日賽事邊界**（見上），原本「開始時間當結束時間」會讓當天的賽事提早變成已結束。

## 已知限制

- **狀態只在使用者重新載入時更新**（畫面閒置時不會自己變）：回到分頁時若距離上次載入超過 2 分鐘會自動重新載入一次；其餘情況按重新整理即可，不需要排程。
- 賽事一旦 `ongoing`／`finished`，**既有報名資料不會被動到**（只擋新報名）；要調整請用管理員的報名管理。
- 報名名單的「候補」行為仍未實作（Roadmap P1-2 報名審核＋候補名單）。
