# v3.0.0 發佈說明

**主題**：後台營運儀表板與效能（統計圖表＋分頁優化＋海報縮圖）

- **日期**：2026-09-26
- **版本**：v3.0.0
- **migration**：`migrations/2026-09-27-v3.0.0-perf.sql`（海報縮圖欄位＋查詢索引，可重複執行）

---

## 一、這版做了什麼

v2.x 把「發佈 → 報名 → 審核 → 候補 → 通知 → 公告 → 場地／工作人員」補齊之後，
下一個缺口是**營運看不見**：沒有總覽數字、列表會隨資料量變慢、手機列表要載大圖。
v3.0.0 一次處理這三件事。

### 1. 📊 營運儀表板（管理員以上）

選單新增「📊 營運儀表板」，一張畫面看懂系統現況：

- **六個關鍵數字**：賽事總數（含報名中／已結束）、報名總數（近 7 天新增）、候補中（含待審核／已核准）、使用者（啟用數、近 30 天登入）、近 30 天未處理錯誤（錯誤／警告分開）、推播成功率（含失敗筆數）。
- **三張圖**：報名趨勢折線、錯誤趨勢折線、賽事分類長條圖。天數可切 7／14／30 天。
- **效能現況**：海報張數與縮圖省下多少流量、列表分頁上限、**這次查詢的實際耗時**（逐區塊列出）、已建立的索引數量。

**設計取捨**：

| 決定 | 理由 |
|---|---|
| 只回聚合數字，沒有任何帳號／email／單筆報名內容 | 儀表板是「看趨勢」用的，不需要也不應該帶個資；測試會檢查回應裡不出現任何帳號名稱 |
| 每個區塊各自 try／catch，缺表只標 `unavailable_sections` | 某張表還沒建（migration 還沒跑）不該讓整個儀表板 500；畫面會說明「哪個區塊讀不到、為什麼」 |
| 結果快取 60 秒，`?fresh=1` 強制重算 | 管理員在畫面上按來按去不必每次全表掃描；「重新整理」按鈕會帶 `fresh=1` |
| 圖表是**手寫 SVG**，不引入任何前端套件 | CSP 是 `script-src 'self'`；幾何在 `public/js/stats.js`（前後端共用），圖上的數字與 API 是同一套算法 |
| 錯誤統計只算近 30 天**未處理** | 已處理的錯誤不該永遠壓著儀表板 |

### 2. 📄 列表分頁與查詢優化

- **分頁是 opt-in**：`GET /api/competitions?limit=50&offset=100` 回 `{ items, total, limit, offset, has_more, returned, paged_by }`；**沒帶 `limit` 的請求行為完全不變**（仍回原本的陣列），既有前端與外部整合不受影響。
- 同一套支援也加到報名名單：`GET /api/competitions/:id/registrations?limit=…&offset=…`（回應多一個 `page` 物件，`registrations` 只回那一頁，`total` 是全部筆數）。
- **`paged_by` 誠實標示分頁位置**：`db`＝資料庫直接切片（成本與頁面大小成正比）；`memory`＝先在伺服器記憶體篩選後切片（例如 `?state=` 是即時推導的狀態、`?status=` 要先正規化舊資料值，資料庫無法可靠過濾）。
- **單次上限**：賽事 100 筆、名單 200 筆（要求更大會被夾住並在回應標示 `capped`），壞參數退回安全預設而不是 400。
- **實際優化**：分頁時報名人數只撈「這一頁賽事」的報名（原本不分頁會把整張 `registrations` 掃回來），成本從 O(全部報名) 變成 O(本頁賽事)；一般使用者分頁時 `total` 只算他自己看得到的筆數（不會洩漏全場總數）。
- 新增 `migrations/2026-09-27-v3.0.0-perf.sql`：報名（賽事／使用者／狀態）、賽事建立時間、錯誤日誌、稽核（動作＋對象、時間）、推播紀錄等索引，全部 `IF NOT EXISTS`；公告已讀與工作人員索引用 `DO` 區塊保護（表不存在也不會失敗）。
- 新增**查詢次數守門測試**：量出賽事列表每次請求固定 3 次資料庫查詢、且不隨賽事數量成長（12 場與 100 場都是 3 次），並禁止對同一張表重複查詢。

### 3. 🖼️ 海報縮圖與列表載入優化

- 上傳海報時，瀏覽器用 canvas **同時產生一張縮圖**（最寬 480px 的 JPEG），一起送到 `POST /api/competitions/:id/poster`（新增可選欄位 `thumbDataUrl`）。**沒有引入任何伺服器端影像套件**（維持零外部依賴）。
- `GET /api/competitions/:id/poster?variant=thumb` 回縮圖；**沒有縮圖就自動退回原圖**並用 `X-Poster-Variant: full-fallback` 標示，呼叫端不必自己判斷。舊海報不需要回填。
- 列表回傳 `poster_thumb_url`，卡片顯示小縮圖（`loading="lazy"` ＋ `decoding="async"`，可點開完整海報）；**視窗外的卡片根本不會下載圖片**（實測驗證：未捲入畫面時 `naturalWidth` 為 0、捲入後才載入）。
- 分享／列印仍然使用原圖（縮圖只用於列表與表單預覽），列印品質不受影響。
- 縮圖上限 250KB：超過就只存原圖並在回應說明原因（`thumb_note`），不靜默忽略；換海報時會清掉舊縮圖（不會出現「新海報配舊縮圖」）。

## 二、需要執行的 migration

`migrations/2026-09-27-v3.0.0-perf.sql` —— **沒跑也不會壞**：

| 情況 | 未跑 migration 時的行為 |
|---|---|
| 海報上傳（含縮圖） | 照常成功，只是不存縮圖；舊的讀取路徑完全不變 |
| `?variant=thumb` | 自動退回原圖（`full-fallback`），不是 404 |
| 列表卡片 | 仍會顯示海報（退回原圖，載入較慢但正常） |
| 營運儀表板 | 照常運作；缺少的區塊會列在 `unavailable_sections` 並在畫面說明 |
| 查詢索引 | 沒有也不會錯，只是資料量大時較慢 |

可重複執行（全部 `IF NOT EXISTS`）；執行後不需要重新部署或重啟（伺服器端欄位探測的負結果只快取 60 秒）。

## 四、修正與發現

1. **伺服器端雙重切片**（開發中發現並修掉）：資料庫已切好一頁後又套用一次 `pageSlice`，導致帶 `offset` 的請求少一頁（offset=95、共 100 筆時回 0 筆）。已用除錯腳本定位並加上邊界測試。
2. **換海報沒清掉舊縮圖**：`thumbReady` 原本只在「這次有帶縮圖」時才探測，導致不帶縮圖的上傳會留下上一張的縮圖（列表會顯示錯的圖）。已改為一律探測並在無縮圖時明確清空。
3. **壞掉的測試圖片**：測試用的 1x1 JPEG base64 其實無法解碼，導致 `naturalWidth` 一直量到 0——是測試資料的問題，不是產品問題。改用確定可解碼的 PNG。
4. **選用資料表缺失沒有回報**：`competition_staff` 不存在時只是少一個數字，沒有告訴使用者原因。已列入 `unavailable_sections`，畫面會說明「資料表尚未建立（migration 未執行）」。
5. **測試替身（假 Supabase）升級**：支援 `limit`／`offset` 切片與 `Content-Range` 總數標頭（原本完全不支援），API 測試才能真的驗到資料庫層分頁。
6. **未跑 migration 的情境獨立成檔**：欄位探測結果在行程內快取，同一檔案先測「有欄位」再假裝「沒有」是測不出來的（沿用 v2.25.0 起的既有慣例）。

## 五、已知限制（誠實說明）

- **索引無法從 API 驗證**：PostgREST 沒有查詢 `pg_indexes` 的介面，儀表板列出的索引清單來自 migration 宣告（畫面標示來源），實際是否建立請用 migration 檔內附的 SQL 查詢確認。
- **`?state=` 篩選時分頁在記憶體進行**：狀態是即時推導的（資料庫無法過濾），回應會用 `paged_by: "memory"` 標示，呼叫端可據此決定是否搭配 `state` 使用分頁。
- **縮圖只在新上傳時產生**：舊海報讀取時自動退回原圖（功能正常、只是沒有省到流量），不回填以避免動到既有資料。
- **儀表板統計是聚合查詢**：資料量非常大時（數十萬筆報名）仍會掃描；目前有 60 秒快取，未來若成長到那個規模會需要改用資料庫端聚合（列入 Roadmap）。
